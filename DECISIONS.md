# DECISIONS.md — append-only judgment log

Format: context → choice → why. One line each (details in linked docs where needed).

## Phase 0

1. **npm registry unreachable (all installs 403)** → build on Node 22 built-ins plus the sandbox's preinstalled global packages (typescript 6, playwright 1.56 + Chromium, pdf-lib), symlinked into `node_modules`; `package.json` still declares them so a normal `npm install` works outside the sandbox → §3.6 says never stall on tooling; this keeps the app runnable *anywhere* with zero installs.
2. **Next.js unavailable** → hand-rolled server-rendered framework on `node:http` (router, middleware, multipart parsing, cookies, CSRF origin-check) in `src/lib/http.ts` → equivalent capability, zero deps; pages are plain functions returning HTML.
3. **React/JSX unavailable for type-safe templates** → `html` tagged-template engine with auto-escaping (`src/lib/html.ts`) → safer-by-default than string concat, no build step, works with Node type-stripping.
4. **Prisma unavailable** → `node:sqlite` + `src/db/schema.sql` written Postgres-compatible + tiny typed query helpers (`db.ts`); `docs/production-port.md` will document the Postgres switch → keeps "SQLite dev default / Postgres-ready" spirit of §3.1.
5. **Auth.js unavailable** → session-cookie auth with scrypt password hashes, hashed session tokens, SameSite+Origin CSRF checks, login rate limiting → meets §9 security bar; RBAC per §4 implemented natively.
6. **Tailwind/shadcn unavailable** → single original design system in `src/ui/theme.css` (tokens: neutral surfaces, one indigo accent) + component kit in `src/ui/ui.ts` → §3.1 asked for a single original design system anyway.
7. **Vitest unavailable** → `node:test` runner; **Playwright IS available** (global install + matching Chromium) so real e2e and screenshots stay in scope.
8. **Zod unavailable** → mini-validator `src/lib/validate.ts` with the same parse/safe semantics used at every boundary.
9. **faker unavailable** → deterministic mulberry32 RNG seeded 42 (`src/lib/rng.ts`) + curated name banks in the seed → §8 requires reproducibility, which this guarantees exactly.
10. **ESLint/Prettier unavailable** → `tsc --strict` (with `erasableSyntaxOnly`) is the lint gate; consistent hand formatting → logged as tooling gap, revisit if registry access appears.
11. **Scheduling model**: all recurring behavior keys off the per-org simulated business date; every job runs once per business day and is internally idempotent; a wall-clock poller merely re-runs the current day → makes the Simulator Console time machine the single source of time, so demos are deterministic.
12. **Business rules in property-local time**: the org business date is the operative date for all properties; property IANA timezones are used for display and timestamp rendering → one clock keeps the demo coherent; per-property date offsets add complexity with no demo value (logged as a production consideration).
13. **Money**: INTEGER cents everywhere; `usd()`/`parseUsd()`/`v.cents()` are the only conversion points; no floats in services.
14. **Sensitive-data hygiene**: password/token/secret fields are excluded from audit diffs; only fake SSN last-4 is ever stored (per §5).
15. **CSRF**: same-origin Origin-header check on browser POSTs + SameSite=Lax cookies instead of per-form tokens → adequate for same-site forms, zero template overhead; API routes use keys not cookies.
16. **Impersonation**: implemented as a new session carrying `impersonator_user_id`, original admin session kept in a backup cookie; bannered in the shell and audited both ways.
17. **Org isolation**: `canAccessProperty` verifies the property's org against ctx before any scope logic (caught by the isolation test suite) → isolation is checked at the data layer, never inferred from role scope.
18. **Seed business date fixed to 2026-07-26** (26th of the demo month, per §8 "the 26th of the current month") rather than wall-clock-relative → deterministic seeds beat calendar-relative ones for reproducible demos; override with STAYLEASED_SEED_DATE.
19. **Replacement reserves = a designated GL cash bucket (1030), not a second bank-fed account**: funding and draws are 1010↔1030 transfers posted on both bases; the BankFeed sim already mirrors non-settlement JEs touching 1010, so every month still reconciles to zero with no sim changes (a second fed account would have duplicated every settlement/AP txn into its feed). `ensureAccount()` backfills 1030 into orgs whose chart predates it; 1030 joined `CASH_CODES` so internal transfers never distort the cash-flow statement.
20. **Owners are read-time reporting dimensions**: ownership percentages scale statements at read time (equity income = share of operating result; capital share = share of 3020 activity in the window); nothing posts with an owner dimension, so the ledger stays one set of books and shares can change without restating history. Per-property assignments are capped at 100% at write time.
21. **Statement packets are saved pulls, not stored files**: a packet row is just scope + basis; the page, CSV, and PDF are computed from the live ledger on demand and streamed — the stakeholder pull stays one click and is always current, with nothing to regenerate or go stale.
22. **Vendor price agreements enforce inside `createPo`**: an in-effect agreed rate silently overrides the supplied unit price on catalog lines (recorded in the PO's create audit as `agreementsApplied`), so every entry path — UI, WO→PO, seed, future API — gets contract pricing without per-caller logic.
23. **Portal provisioning is one idempotent function** (`ensurePortalAccess`): email-keyed — no email is a graceful no-op, an existing account by that email gets linked (never duplicated), a fresh account gets a minted credential + recorded invite exactly once. Live orgs get real one-time passwords (`tempPassword()`), demo orgs keep `demo1234` so the public demo stays enterable. Every resident entry path (three import lanes + lease activation + the resident-page button) calls it, so no path can create a resident who can't sign in.
24. **The Message Console is readable by live orgs** (GET routes keep the `dev:console` perm but drop `devOnly`; the simulator and inbound-reply POST stay demo-only): until live email/SMS rails ship, the outbox record *is* the delivery mechanism — staff open the invite, read the one-time password, and relay it. Hiding it behind demo-only made live credentials unreachable by design.
25. **The demo is demoted, not gated (yet)**: the sales motion is demo-led — every primary CTA books a call — but the self-guided demo remains publicly enterable, so the verification band's "Live demo, open to anyone" stays literally true. The honesty rule that travels with this: no marketing copy may say "no sales call" while every primary button asks for one — that phrasing was removed everywhere ("no signup, no sales call", "No form first"). When the access-code gate ships, the verification item must be rewritten in the same commit.
26. **The homepage argues control before capability (v4)**: the approval band sits directly under the hero because the AI-skeptical buyer's first objection ("AI talking to MY tenants?") must be answered in the first viewport-and-a-half, not in section 07 — the h1 keeps the autonomy claim, and the very next band shows the leash. Corollary: the hero vignettes and the approval band may not duplicate the same moment; the 9:04 pm Zillow draft belongs to the approval band, the hero shows breadth (Ask, collections, 2:14 am maintenance triage).
27. **The xlsx parser is a correctness foundation, not a convenience**: self-closing-tag handling is done with lazy attribute captures and row padding by `r=`, with a regression test that hand-builds the malformed-looking-but-legal shapes real systems emit (styled empty cells everywhere). Any future parser shortcut must survive the Yardi fixture — a parser bug upstream of the AI reader corrupts everything downstream while looking like an AI problem.
28. **A rent roll's rent is the rent-CODE's amount, not the unit row's Amount cell**: Yardi's block format puts an arbitrary charge (often parking) on the unit row. The harvest gathers each block's charges, infers the portfolio's rent code (modal across blocks, rnt*-prefixed tie-break), promotes it into the rent column, and folds the rest into "Other monthly charges" — billed as a separate lease_charges line so rent analytics stay honest and nothing the prior system billed monthly is lost.
29. **Applied imports are records, not ghosts**: a batch that ran stays visitable read-only — status, result summary, and the exact mapping used — because operators audit their own onboarding ("what did that file do?") and support conversations start from it. The review screen and the record are the same data, different affordances: staged = forms + Apply, applied/discarded = facts only.
30. **Agent metrics live in scorers OUTSIDE the agents**: deterministic rules score into named buckets with a persisted reason sentence; agents read the latest assessment as a fact and compute no severity of their own; every scorer ships shadow-first (assessments + chips, zero behavior change) and gains behavior only per-org via its mode setting. Rules score, models phrase, humans decide the regulated moments — the same split screening already uses.
31. **Two spec-to-code deviations, recorded**: the "no payment in 21 days" engage-trigger was dropped (at monthly-rent grain a 21-day gap is a normal cycle; age ≥ 15d subsumes the real signal), and "pause autopay retries on escalate" is a no-op (runAutopay fires once per enrollment per month — there are no retries to pause).
32. **Active mode retires the 'final' dunning tone**: the legacy >45-day "final" band is exactly the escalate bucket, and past the notice threshold the AI writes nothing resident-facing — it assembles a staff packet whose approval opens the collection case. Adverse-action-adjacent moments get the least AI, by design; the packet's confidence is pinned at 0.6 so no autonomy dial can ever auto-execute it.
33. **Lead heat is decided by behavior and inventory only — never source, never text**: `LeadHeatInputs` is structurally text-free (intent booleans, fit, counts, dates), so protected-topic content cannot move a bucket even by accident, and `source` is recorded for analytics but excluded from every rule. Chips modulate staff effort; they never change what any prospect is told. The regression test asserts a voucher mention produces identical inputs and an identical bucket.
34. **Buckets modulate effort, ordering is behavior**: shadow mode shows chips but leaves Leasing Center ordering untouched, because reordering a work queue IS a behavior change. Active mode buys ordering + the call task, nothing else — cadence pausing and the waitlist job stay future work so the first active flip changes the smallest reviewable surface.
35. **Removing an upload deletes the document, never what it imported**: the Migration Center's Remove takes the `import_batches` row — which is not a pointer to the file but the file's contents, the whole grid with every name, email, phone and balance in it — plus the lease lane's stored PDFs, and leaves every property, unit, lease, resident and journal entry the apply created, because those are the portfolio now and no longer the document. This **amends #29**: that rule governs what the SYSTEM does on its own (an applied batch is never auto-hidden or redirected away from), while a deliberate operator removal behind a typed-name confirm is a different act with a different actor. The audit event carries metadata forward — kind, filename, status, row and file counts — and never contents, so "what was that upload?" outlives the record it removed. Ceremony scales with consequence: staged and discarded uploads wrote nothing, so the confirm screen IS the confirmation; applied uploads take the typed file name, matching the property danger zone, because their record is the only remaining account of an event that changed the books. Corollary for data hygiene: deleting a stored file means the blob AND the row, together (`deleteFiles`) — a row without bytes is a dead download link, and bytes without a row are unreachable data that still holds resident PII.
36. **Removing an upload takes back what it imported — by provenance, not guesswork** (supersedes the corollary in #35): every row an apply writes now carries `import_batch_id`, so removal deletes exactly the rows this upload created and nothing else. Henry's call, and the right one: the typed-name confirm is already the gate, so making an operator delete the property separately to undo an import was busywork that left the two halves free to drift apart. Three mechanisms, chosen to avoid duplicating a cascade that already exists — (a) properties the import CREATED are handed to `deleteProperty`, the ~80-table books-safe cascade that already refuses when real payments or manually posted journal entries landed on them; (b) rows added into properties that already existed are deleted by their stamp in dependency order, narrow by design, with `PRAGMA foreign_keys=ON` as the backstop that turns "something downstream now references this" into a refusal rather than an orphan; (c) contact merges have no row to delete — the directory lane fills BLANK fields on people who already existed — so the undo is blanking those fields back, and only where the value is still the one the import wrote, because anything edited since belongs to the operator. Money is the hard rail: a payment recorded against an imported lease refuses the removal outright. The honest limit, surfaced in the UI rather than papered over: an import applied BEFORE the stamp existed has no traceable footprint, so its confirm screen says so and points at the property danger zone instead of implying an undo it cannot perform.
37. **An upload removes the property only if the upload CREATED it** (the corollary Henry asked for out loud, so it is written down rather than implied by #36): a rent roll that stood a building up owns that building — remove the upload and the property goes with every unit, lease, resident and journal entry under it. An upload that merely added to a building someone else created — a lease PDF, a second rent roll, a directory, opening balances — owns only its own rows, and removing it leaves the property standing. The alternative (any source document's removal deletes the property) fails the obvious case: pulling one lease PDF out of a 110-unit building must not delete the building, and would destroy rows that other uploads created. Because that distinction is invisible from the outside, the confirm screen states it by name in both directions — "**Station U&O** was created by this upload, so it goes too" / "**Cedar Yard** stays — this upload didn't create it" — so the operator never has to infer which case they are in from a count.
38. **Graph tooling is installed project-scoped and degrades to nothing**: graphify lives in `.claude/` in the repo — not a user profile — so every session and every clone gets the same skill and hooks without per-machine setup, which is the only form that works for a repo several Claude sessions build on concurrently. Two rules travel with that. (a) **The tool is optional, always**: the installer's absolute hook path (`/root/.local/bin/graphify`, real only inside one ephemeral container) is replaced by a `command -v graphify` guard, so a machine without the CLI gets a silent no-op instead of a hook error on every file read — committed tooling may not make the repo harder to work on for someone who hasn't installed it. (b) **The graph is generated, not committed**: `graphify-out/` is gitignored because it is 14M of derived artifact that rebuilds from source in 12s, and a checked-in graph is a stale graph the moment anyone lands a commit. Corollary on the doctrine text itself: the installer appends a CLAUDE.md section asserting the graph exists, which is false on a fresh clone — the section was rewritten to state what is committed versus what must be built, because this file is the engineering memory and an inherited claim is still a claim.
39. **The web container is provisioned by a hook, and the hook may never block a session**: `.claude/hooks/session-start.sh` installs node deps and the graphify CLI and builds the graph, because Claude Code on the web clones fresh every time and a session that starts without `node_modules` reports phantom typecheck failures that look like real ones (five of them, live, in the session that wrote this). Three rules make it safe to commit. (a) **Web only** — the `CLAUDE_CODE_REMOTE` guard exits 0 and silent on a local machine, so committed tooling never installs anything on a developer's box uninvited; this is the same principle as #38's `command -v` guard, applied to provisioning rather than invocation. (b) **Never fatal** — every step degrades to a `WARN` line, because a broken setup script that prevents a session from starting is strictly worse than the tools it installs being missing. (c) **Idempotent and cheap when warm** — SessionStart fires on resume, clear and compact as well as startup, so the graph rebuild runs only when a file under `src`/`tests`/`e2e` is newer than `graph.json` (0.35s warm vs 9.5s unconditional). The synchronous mode is deliberate: async would start the session while `npm install` is still running, which reintroduces exactly the phantom-failure race the hook exists to remove.
40. **The org-level "clear all portfolio data" is the onboarding loop's reset, and it is allowed to force**: getting a real portfolio in takes several tries — a mis-mapped rent roll, a directory in the wrong name format — and clearing up after a bad attempt one property at a time is exactly the chore that makes an operator stop testing and start living with bad data. So the reset deletes every property (through `deleteProperty`, once per property, so the tested cascade stays the only thing that knows the ~80 tables) plus the org-level residue a property delete leaves standing by design: vendors, their price agreements, and the Migration Center's uploads with their stored files. It passes `force`, unlike the per-property delete: the payments-and-manual-entries rail exists to stop someone erasing financial history for ONE building while the rest of the books carry on, and there is nothing left to protect once the whole portfolio goes. What survives is deliberate — the organization, staff accounts and roles, the chart of accounts, settings, and the audit trail, which records the clear and must outlive the data it describes. Demo orgs are refused outright rather than gated: the seeded world is what the public demo at stayleased.com runs on, and no typed confirm should be able to take it down. The flash lands the operator on the Migration Center, because the only reason to clear is to import again.
41. **Org settings get one spec per setting, and that spec drives both the form and the parse**: the page rendered all ~40 keys as raw JSON in text boxes, which put `bah_table` at the same visual weight as the late fee, offered no units or bounds, and made a typo in `late_fee_policy` a silent change to what every resident is charged. `settings_spec.ts` now describes each key once — group, plain-language label, what changes in the product when it changes, and the control it deserves — and rendering and parsing are both generated from that one description, so a control and its validation can never drift apart. Money is entered in dollars and stored in cents (#13 holds: `parseUsd` is still the only conversion), days as days, percentages as percentages; a bad value comes back as a sentence about that setting rather than a JSON parse error. Henry chose the full treatment over an Advanced escape hatch, so nothing accepts hand-written JSON: `payment_application_order` is numbered positions, weekday arrays are checkboxes, and `bah_table` is a small matrix with add and remove. Two rules that keep it honest as the product grows: schema-ish object fields (`screening_criteria.version`) are declared `preserve` and carried through a save untouched rather than being editable or silently dropped, and `specCoverage()` is asserted in the test suite so a new key in SETTING_DEFAULTS cannot ship unrendered and a renamed one cannot leave a dead control behind. The answer to "should it be editable?" is yes: these are the operator's own policy decisions, and the alternative is emailing support to change a late fee.
42. **Two rules the settings rebuild had to learn the hard way, from code review**: (a) *a control may only offer what the engine implements.* The late-fee select was authored from the shape of the default object rather than from `lateFeeCandidates`, so it offered a "daily only" structure the engine has no branch for — choosing it would have silently assessed no late fees at all — while omitting `percent`, which the engine does implement, so an org on a percentage policy would have had it rewritten to flat on the next unrelated save. A control is a promise about behavior; it is authored against the consumer, not the default. (b) *a screen that shows an effective value must merge the levels it is showing.* `getSetting` replaces a stored object wholesale, so a property overriding only `ai_autonomy.leasing` rendered the other three dials as code defaults — and saving that screen would have pinned them, silently downgrading autonomy the org had set. `layerSetting`/`getSettingMerged` now hold the merge rule in one place, and the page reads both levels in one query and layers them. The general form: any editor that round-trips a value must render exactly what a save will write.
43. **Closed-shape settings merge across levels; open-ended key maps replace** (found by adversarially verifying #42b rather than by trusting it): layering org over default is right for a setting whose fields are fixed — a property overriding one autonomy dial must not render the other three as code defaults — but it is wrong for `bah_table`, whose keys are DATA. Merging a stored table over the default re-supplies any pay grade the operator just deleted, and the next save writes it back, so deletion becomes impossible. A merge cannot express "this key is gone". The spec already carries the distinction (`subs` = closed shape, `matrix` = open-ended), so the page reads it from there on both the render and the parse path. Corollary recorded, not fixed: only the settings page merges — every runtime consumer still calls `getSetting`, which replaces wholesale. That is not a live divergence today (the sole code writing partial property rows is m17's `ai_autonomy`, and its consumer `autonomyFor` merges for itself), and saving any setting through the page writes a complete object, which brings the runtime into agreement rather than out of it. If partial property rows ever spread beyond `ai_autonomy`, the fix is to teach `getSetting` the same closed-shape/open-ended split — not to add a second merge at each call site.
44. **The settings level that needs the most protection is the one with no property attached**: the first scope fix guarded the `property` parameter and left `property=''` — the organization defaults — open to anyone holding `admin:settings`, which is the level that reaches EVERY property, including ones outside a property-scoped admin's grant. A scoped admin could not touch another building's override but could rewrite the default that building inherits. Org defaults are now readable by a scoped admin and writable only with `allProperties`; their own properties stay fully theirs. Recorded and not fixed here: `admin:settings` and `admin:staff` travel together in the role model, so a determined property-scoped ORG_ADMIN can still widen their own grant and come back — closing that means changing the role model, which deserves its own build rather than a patch inside a settings page.
45. **Validate a control the way its consumer reads it, not the way the input type suggests**: a `type="time"` field looks validated by the browser, but `99:99` matched the settings page's own `\d{2}:\d{2}` and reached `inQuietHours`, which does `parseInt(start.slice(0,2))` — making the quiet window never open instead of failing loudly. Same shape elsewhere: `parseInt` accepted `0x10` as 0 for any min-0 integer; a blank comma list stored `[]` and silently switched lead follow-up off; a missing field (rather than a blank one) let a truncated post clear a text field it never mentioned; and money had no ceiling, so a misplaced decimal could post a $1e12 threshold into the books. Every control type now parses strictly, refuses absence when the form always submits it (checkbox-backed types excepted, since absence IS the value there), and carries a ceiling where the value flows into money or arithmetic.
46. **Irreversible side effects belong on `afterCommit`, not after `tx()` returns** (found by the critic agent refuting the fix that was supposed to establish exactly this): `tx()` nests via savepoints, so a nested call returning is a RELEASE, not a commit. `deleteProperty` unlinking "after its transaction" therefore unlinked while `clearOrgData`'s outer transaction was still open — reproduced as row=true/blob=false after a rollback, precisely the dead-download-link state the fix was written to prevent. `db.ts` now exposes `afterCommit(fn)`: queued while any transaction is open, run once the OUTERMOST one commits, dropped on rollback, and executed immediately outside a transaction so callers need not know their context. A throwing callback is swallowed — the data is committed, and a failed cleanup must not read as a failed write. Corollary: the global orphan-blob sweep is deleted rather than fixed. Every database in a checkout shares `data/files`, so sweeping while pointed at one unlinks bytes owned by rows in another (it wiped `e2e.db`'s files when run from a scratch database). The file store has no database affinity; orphans can only be collected by an id the caller owns.
47. **A property override stores what DIFFERS, not a copy of the effective value**: rendering merged levels fixed the display, but saving still wrote the whole object back, so an operator changing one autonomy dial silently stopped the other three from tracking organization-wide changes — reproduced by submitting the rendered form byte-for-byte with no edits and watching three unset dials become pinned. The save now narrows to the fields that differ from the organization's effective value, and an override that differs in nothing is deleted rather than stored, which is what the page's own copy promises ("clearing it hands that setting back to the organization"). Open-ended key maps are exempt: a diff cannot express a deleted row.
48. **Settings are organized by where the answer comes from, and the documents answer most of them** (Henry: "too many and way too complicated… I want the AI to know what settings there are based off the documents uploaded"): grouping by domain told an operator that a setting was about Deposits, but not whether it was their decision, their lease's decision, or their state's. All forty therefore looked like homework. The page now splits on the only axis that reduces the work — **from your documents** (your leases state the late charge, its grace period, the returned-payment fee, pet rent and deposit, the notice period, the insurance minimum: the AI reads them and proposes, you confirm against the quoted sentence), **set by where you operate** (statutory, so the page says so and names the state), and **your call** (the genuinely discretionary set, which is the only bucket that should look like a settings form). Three rules hold the feature honest. Reading is never writing: a proposal changes nothing until a human accepts it, and every proposal ships with the sentence it came from so the operator confirms against the source rather than trusting a number that appeared. Silence is never a value: a policy no document states produces no proposal, because proposing $0 for an unstated fee would be inventing one. And documents that disagree say so — the modal value is proposed at low confidence naming what the others said, because a portfolio running two late-fee regimes is a fact the operator needs, not a tie for code to break quietly. The reader is deterministic regex over sentences for the same reason the scorers are: a value that decides what a resident is charged must be reproducible and explainable, with the AI lane able to fill gaps but never to be the only reader. Never derived, by design: screening criteria (fair-housing sensitive, must be authored deliberately) and the AI autonomy dials and approval thresholds (those are the leash, and a document does not set the leash).
49. **The jurisdiction bucket flags, it does not assert** (Henry's call, offered against shipping a state-law table): telling an operator "Colorado requires deposits returned in 30 days" is a legal claim the product would then own and have to keep current as statutes change — and the honesty rule already forbids claims the product cannot stand behind. So the section names which settings are law rather than preference, names the states the portfolio operates in, and asks the operator to confirm against the statute. That keeps the useful half — you cannot know a deposit deadline is not a matter of taste unless something tells you — without the product asserting law it would be responsible for.

50. **A setting is per-property only where the code that acts on it reads it per-property, and that is now a build gate rather than a habit**: `/admin/settings` offered all 40 settings at the property level and stored overrides correctly, but the override reached nothing in 20 places — 7 reads passed no property id at all (with `lead.property_id` or `lease.property_id` sitting in scope), and 13 read an object-valued setting with `getSetting`, which REPLACES a stored object wholesale while #47 stores overrides as partial diffs. The second is the dangerous half: a property that edits one box leaves every sibling field `undefined` at runtime, so `addDays(due, undefined)` threw `RangeError` out of `lateFeeCandidates` and killed the nightly late-fee job **for the whole organization**, `hours.days.includes(...)` 500'd the **public** tour-booking page, a partial `convenience_fee` computed `NaN` onto a real payment, and a partial `screening_criteria` silently skipped the income test and the eviction lookback on the adverse-action path. Every one of these had passing tests: the settings page was verified with whole-object saves, which is not the shape an operator produces by editing one box. Same lesson as the import build, in a second place — **verification must exercise the path production takes**. The fix is the rule, not the instances: `tests/settings_scope.test.ts` scans every `getSetting`/`getSettingMerged` call with a literal key and fails the build when an object setting is read at a property without merging, or when a property-overridable setting is read with no property — the bargain `specCoverage()` already makes for unrendered settings. Alongside it, five behavioural tests drive a *partial* override through the real consumer (`lateFeeCandidates`, `tourSlots`, `inQuietHours`, `academicCalendar`, `depositDeadline`), because a lint proves the call shape and only a run proves the value. Two adjacent bugs surfaced while verifying and are fixed with it: `currentCriteriaVersion` read criteria per property but wrote the version row at `property_id=''`, so two properties with different criteria alternated one org-wide row, bumping the version on every application and printing an unstable number on a notice that claims to be "applied consistently to all applicants"; and `depositDeadline` detected "the operator chose this" by comparing the value against the literal `30`, so a property that deliberately chose 30 days had its override discarded — "has someone chosen a number here?" is a question about the settings table (`settingIsExplicit`), never about the number.

51. **What cannot vary by property says so, at the property level, in the operator's terms**: three settings are read once organization-wide by design — the AI kill switch (one that stopped only some buildings would not be a kill switch), lead-heat scoring mode (the Leasing Center lists leads across the portfolio and **ordering is behavior**, per #34), and the BAH rate card (read on a portfolio hub with no property in view) — plus `delinquency_scoring.mode`, which is org-wide while `noticeThresholdDays` beside it in the same key is per-property. Offering these as property controls was worse than not offering them: the save succeeded, the row was stored, and the operator came away believing it was set. They are now declared `orgOnly` on the spec (whole setting or single field), rendered at the property level as a **statement of the organization's value** with the reason and a link to change it there, and refused by the endpoint even if the form is forged. The declaration is not a comment: the scope lint holds it to the code in both directions — an `orgOnly` setting may never be read with a property id, and a setting that is not `orgOnly` may never be read without one — so the page and the product cannot drift apart again. Scorer modes read through a named `scorerMode()` helper for the same reason: a deliberate org-wide read should look deliberate, not like a forgotten argument. Corollary on the picker: which level you are editing is a mode, not a filter, and an organization default reaches every building — so the level is a bar with its own colour rail, named in the eyebrow, carrying each property's override count, sticky under the top chrome above every section #48 introduced, and **every Save button names the level it saves to** ("Save for The Foundry Lofts" / "Save for Summit Ridge Management Co."), because by the time an operator scrolls to the late fee they can no longer see the control they set on the way in.

52. **CI retries the unit suite exactly once, and announces it**: `tests/accounting.test.ts` carries a documented date-ordering flake that reddens roughly one full-suite run in three and passes on re-run, which is why CLAUDE.md already tells a human to re-run before believing a red. A job that cries wolf every third run gets ignored, and an ignored gate is worse than no gate — so the workflow encodes the same rule the human follows: run, and on failure run once more. Two consecutive failures is a real failure. The retry emits a warning annotation rather than passing silently, so a flake that becomes constant surfaces as a pattern in the run history instead of being absorbed into green. This is a workaround for a known bug and not a fix: the flake still owes a root cause, and the annotation is what keeps that debt visible rather than letting CI paper over it.

53. **The "date-ordering flake" was a money bug, and CI is what proved it**: `voidApPayment` selected the journal entries to reverse with `posted_at >= (SELECT created_at FROM ap_payments WHERE id=?)` — a comparison between two `nowIso()` calls taken on either side of a single insert, to pick the live generation of entries for an invoice that may have been paid more than once. Whether they landed in the same millisecond was a race. When the payment row's timestamp came out later than its own entries', the query matched nothing, so **the void reversed nothing and the reissue still cut a check: the ledger showed the cash leaving twice.** It had been logged for months as a test flake to re-run, on the strength of passing when re-run — which is exactly what a coin flip does. The first CI run failed it twice consecutively on a different machine, and two in a row is what distinguished a real bug from randomness. The fix removes the clock from the decision entirely: the live generation is the one nothing has reversed yet (`NOT EXISTS (… WHERE reversal_of = je.id)`), which is exact, deterministic and expresses the actual intent. Two regression tests, one forcing the losing race and one voiding a reissued payment to prove only the live generation reverses; both were confirmed to fail against the old query before being trusted. Corollary, recorded because it will be tempting later: the CI unit step was born with a re-run-once for this flake and that retry is now **deleted**, not kept as insurance. Its whole justification was a bug that no longer exists, and a retry kept "just in case" is the mechanism by which a suite learns to hide the next real failure.

54. **The e2e browser asks for reduced motion, because a promise no test makes is a promise the product breaks**: `.content` — the wrapper around every screen in the app — carried a `pagein` entrance that the `prefers-reduced-motion` block never turned off, so the motion doctrine's "reduced-motion = visible + still" was false on every page, live, and 31 e2e files walked past it. They walked past it because Playwright launches with no motion preference: every suite only ever exercised the animated path, so the reduced half of a two-branch doctrine had no coverage at all. `newPage()` now sets `reducedMotion: 'reduce'` on the context, which makes reduced motion the state the whole suite is written against and the stillness promise enforced rather than inspected. Two consequences worth having recorded. The suite got faster (9m58s from about 12) because Playwright's actionability check waits for elements to be **stable**, and an entrance animation on the page wrapper means paying that wait on every navigation — which is also how this surfaced: as a 30s click timeout in `reports.test.ts` that read like a slow test and was a doctrine violation. And the animated path is now the untested one; that is the correct trade, since it is the branch a human sees constantly and the reduced branch is the one written for people who will never file a bug about it, but it is a trade and not a free win.

55. **Never assert on a window whose width is an animation**, and put the guard where the handler can honor it: `ai.test.ts` checked the Ask chat's double-send guard by clicking send and waiting for `.aichat-panel.busy` to appear. That worked only because the typewriter held the state open for seconds — take the typewriter away (#52) and the busy window shrinks to one in-process round trip, so the assertion started arriving after it had closed. The app was correct; the test was measuring an artifact. It now holds `/ask.json` in flight with a route, which makes the busy state a fact the test controls rather than a race it hopes to win, and then asserts the guard by behavior instead of by class name. Doing that found the hole the old assertion could not see: `ask()` refuses while busy, but the submit handler clears the input **before** calling it, so a question typed during an answer was wiped and never sent. Today it is unreachable — the send button is disabled and Enter's implicit submission clicks that same disabled button — which is precisely the argument for fixing it, because the disabled attribute is an affordance for the operator, not an invariant for the code, and `requestSubmit()` already walks around it. The general rule: a guard that only exists in the UI layer is one refactor from not existing, and a test that proves the guard by watching the UI layer will not notice when it stops.

56. **`newPage()` is the only door to a browser page, and a test asserts it** (the corollary #52 needed and did not have): setting reduced motion in the helper made it the mode the suite runs in — for the 29 files that use the helper. Three call sites did not. `askdock`'s two theme pages needed a `colorScheme`, the helper took no such option, so they called `browser.newPage({ colorScheme })` and inherited none of the viewport, scale or motion settings; `ilsemail` had done the same with a bare `browser.newContext()`. Those pages therefore kept the animated path after the rest of the suite left it, and the theme toggle failed Playwright's stability check on a 2-core hosted runner while passing on every developer machine — invisible exactly where the change was made, visible only where the gate runs, which is the whole argument for having the gate. The fix is the shape, not the two patches: an option a test genuinely needs to vary becomes a parameter on the helper, and `tests/e2e_hygiene.test.ts` fails on any direct `browser.newPage`/`browser.newContext` under `e2e/`. The general rule this repo keeps relearning in new costumes — a setting that must hold for every case has to live somewhere every case is forced through, because a convention that 29 of 31 files follow is not a setting, it is a habit. Measured, since it justifies the whole line of work: reduced motion took the hosted-runner suite to 6m38s, from two consecutive runs cancelled at a 40-minute cap.

57. **A web-UI upload is a whole-file replace, so the append-only logs must never travel that way**: `6fef829` ("Add files via upload") carried a genuine build — property-scoped settings, 24 files, its own tests — and also silently deleted two BUILDLOG entries and decisions #50 and #51, because the uploader's copy of those files was read before #7 merged and the upload overwrote rather than merged. The lost #51 was the AP void money bug: the single most expensive thing the project learned that day, and the reason a "known flake" is no longer in CLAUDE.md. Nothing failed — `doclog.test.ts` checks that numbers are contiguous and headers unique, and a clean overwrite satisfies both, so a file can lose two entries and still pass every gate. CLAUDE.md already warned that dot-directories do not survive a web upload (that is how `ci.yml` was lost the first time); this is the same hazard with a quieter failure, and the rule generalises: **an upload can only be trusted for files the uploader's session actually authored end to end.** BUILDLOG.md and DECISIONS.md are never that, by construction — they are the one place every parallel session writes. So they go up as a patch on a fetched tail, or as the paste-in file the parallel-session rule already prescribes, never as an upload. Recorded here rather than only in CLAUDE.md because the next session to reach for the upload button will be reading a diff, not the manual.

58. **Nothing in an inline script may contain a closing script tag — including a comment about closing script tags** (found the hard way: the portfolio map lost every pin, and the only signal was "Unexpected end of input" with no line number, on a tree where `tsc` was clean and 351 unit tests passed): a `<script>` element's body is *raw text*, so the HTML parser ends it at the first closing sequence anywhere inside — string literal, regex, or comment. The comment that killed the map was explaining the very hazard it triggered. Everything below the cut is reparsed as markup and silently vanishes, which is why this class of bug reads as "the feature stopped working" rather than as a syntax error. Fixed structurally rather than by rewording the comment: `inlineScript()` in `lib/html.ts` escapes the slash, and `<\/script` is byte-identical to JavaScript in every context the sequence can legally appear — in a string it is the same string, in a comment and a regex the extra backslash changes nothing that runs — so it can be applied blindly to every inline script instead of auditing each one. Corollary for the gates: a clean typecheck and a green unit suite say nothing about whether client JavaScript parses. Only loading the page does. This build's browser probe is what caught it, and it caught it before the e2e suite did.

59. **A select that omits the value it was handed will silently change it**: refining the property time-zone picker to the four continental zones would have dropped `America/Phoenix` from the list — and a picker that does not contain the stored value posts a *different* value back the first time anyone edits an unrelated field on that form. An Arizona property would have relocated itself to Denver during an address correction, with no error and no audit trail distinguishing it from an intentional change. `timezoneOptions(current)` therefore appends any stored zone outside the four, labelled "current setting", so the list is short for the common case without being lossy for the uncommon one. The general rule: narrowing an option set is only safe if existing values are preserved as options, because HTML forms have no way to express "leave this alone".

60. **The board refuses the gesture rather than accepting it and failing** (unit board drag-and-drop): `occupied` and `notice` are derived from lease events, so dragging a card into or out of those columns can never succeed. Two ways to build that — accept every drop and report the refusal after the round trip, or make the illegal columns non-droppable and the affected cards non-draggable. The second is the honest one: a column you can drop into is a promise, and a board that takes the card and then hands it back has told a small lie about what it can do. The server still enforces the rule (`MANUAL_UNIT_STATUSES`, read by both the board route and the unit page's status form, so the two can never drift), because a disabled affordance is a courtesy and not a control. Same principle in the bid comparison: an expired COI disables Award in the markup *and* throws inside `assignWo`, and the award runs in a transaction so a blocked dispatch leaves no bid marked awarded.

61. **Ask StayLeased is a companion, not a modal** (Henry: "shouldnt blur the surrounding screen so you can still visit other pages with it open"): the panel had a scrim and a backdrop blur, which made the page behind it both unreadable and unclickable. That is exactly backwards for this feature — the questions people ask it are *about what is on the screen*, so checking the answer against the page should not require dismissing the answer. The scrim is gone in both states, the overlay root is pointer-transparent and only the panel takes events, and pinning docks it beside the content by giving up layout width on `.app` rather than covering content. The conversation rides along in sessionStorage, because "keep it open while I visit other pages" delivers an empty panel if the panel forgets what you just asked. Closing unpins and clears: the close button has to mean close, not "hide until the next navigation".

62. **A test that fails intermittently has not been explained until something has been measured against a clean tree** (this build spent real time on `tests/accounting.test.ts`, which `CLAUDE.md` documents as a known date-ordering flake that "passes solo"): it does not pass solo — 3 failures in 6 consecutive solo runs — and the stash-and-compare that followed showed the identical 3-in-6 on an unmodified tree, which correctly cleared this build. But "not mine" is not "not real". A parallel session (PR #7, DECISION 53 — the fix) pointed CI at it and found the money bug underneath: `voidApPayment` picks the entries to reverse with `posted_at >= (SELECT created_at FROM ap_payments WHERE id=?)`, and those are two `nowIso()` calls straddling one insert. Lose the race and nothing matches — the void reverses nothing, the reissue cuts a new check regardless, and the books show the cash leaving twice. The standing instruction to re-run before investigating is what kept that behind the word "flake" for as long as it lasted. Re-running answers "does it fail again"; only stash-and-compare answers "did I cause it", and neither answers "is it real" — that takes reading the failure. A recurring failure earns a diagnosis, not a label.

63. **Search that returns results and does nothing on Enter is a broken search box**: the command palette required an explicit ArrowDown before Enter would navigate, so the natural gesture — type a resident's name, press Enter — silently did nothing. The top hit is now selected the moment results land, and Enter honours a query whose results are still in flight instead of swallowing the keystroke. Two absences were as damaging as the bug: nav destinations were not indexed at all (typing "dispatch" found nothing, though the dispatch board is a page in the product), and neither were vendors (typing a plumber's name while they were on the phone found nothing). Pages rank below records and match on prefix or word-start only — substring matching turns every two-letter query into a wall of navigation.
